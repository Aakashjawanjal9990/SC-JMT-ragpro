## 1. Executive Summary & Purpose

The primary objective of the **Data Ingestion Module** is to convert raw, heterogeneous, and potentially noisy Indian Supreme Court judgment PDFs into clean, structured, and strictly traceable JSON contracts. 

Every single text passage generated by this pipeline is permanently linked to its:
1. **Source Document ID** (`document_id`)
2. **Original PDF Page Number** (`original_page_number`)
3. **Sequential Chunk Index on that Page** (`chunk_index`)
4. **Active Legal Section Heading** (`section_heading`)
5. **Case Metadata** (Case number, parties, bench, date)

This traceability enables downstream retrieval (**Pratik**) and answer generation (**Nilesh**) to guarantee **grounded answers** with exact page-level citations back to the source PDF displayed in the frontend (**Tanvi**), honoring the core system principle:
> *"Every answer must be traceable to source evidence. An honest limitation is better than an unsupported legal claim."*

## 3. The Parsing Process in Detail

### 3.1 Dual-Engine Parsing Architecture
The system supports two complementary extraction engines:

| Feature | Engine 1: LlamaParse Cloud (v2 REST API) | Engine 2: Local PyMuPDF (`fitz`) + OCR Fallback |
| :--- | :--- | :--- |
| **Best Used For** | Complex multi-column pages, tables, scanned images, historical prints. | High-speed processing of modern digital PDFs; offline execution. |
| **Output Format** | Structured Markdown with heading tags (`#`, `##`) and table grids. | Plain text lines with rasterized OCR fallback. |
| **Speed** | Cloud API call (~2–4 sec / doc). | Ultra-fast local execution (~10–50 ms / page). |
| **Cost / Connectivity** | Requires Internet & API Key (`LLAMA_CLOUD_API_KEY`). | Completely offline; zero external API dependencies. |
| **Failover Role** | Primary engine when `--use-llamaparse` is enabled. | **Automatic failover engine** if LlamaParse network fails. |

---

### 3.2 LlamaParse v2 Cloud Pipeline Implementation
Integrated in `extractor.py` via `LlamaParseExtractor`:
1. **Multipart Upload**: The PDF file is posted to `https://api.cloud.llamaindex.ai/api/v2/parse/upload` with Bearer token authentication and payload:
   ```json
   {
     "configuration": "{\"tier\": \"cost_effective\", \"version\": \"latest\"}"
   }
   ```
2. **Job Initiation**: The server returns a job ID (e.g. `pjb-qs90sj3j...`).
3. **Asynchronous Polling**: The client polls `https://api.cloud.llamaindex.ai/api/v2/parse/{job_id}?expand=markdown` every 1–2 seconds until `"status": "COMPLETED"`.
4. **Page Mapping**: The response provides `markdown.pages[]` with explicit `page_number` (1, 2, 3...) and clean `markdown` strings, ensuring 100% fidelity to the physical PDF pages.

---

### 3.3 Local PyMuPDF Extraction & OCR Fallback
Integrated in `extractor.py` via `PDFExtractor`:
1. **Selectable Text Extraction**: Extracts text page-by-page using PyMuPDF’s `page.get_text("text")`.
2. **Density Check**: If extracted text length is $\ge 50$ characters (`MIN_TEXT_LENGTH_THRESHOLD`), selectable text is accepted.
3. **Automatic OCR Trigger**: If text length is $< 50$ characters (scanned image page or corrupted font encoding):
   * First attempts PyMuPDF built-in OCR (`page.get_textpage_ocr(dpi=200)`).
   * Falls back to PIL + Tesseract OCR via `pytesseract.image_to_string` on a 200 DPI pixmap.
   * Logs the page number in `ocr_applied_pages` for QA tracking.

## 4. The Cleaning Process in Detail

Implemented in `LegalTextCleaner` ([`cleaner_chunker.py`](file:///E:/Dummy/cleaner_chunker.py#L48-L82)):

### 4.1 Strict Cleanup Principles
1. **Zero Semantic Drift**: Never rephrase, summarize, or alter statutory terms or judicial reasoning.
2. **Hyphenation Reassembly**: Fixes words broken across line wraps (e.g., `repre- \nsentative` $\rightarrow$ `representative`):
   ```python
   re.sub(r'(\b[A-Za-z]+)-\s*\n\s*([A-Za-z]+\b)', r'\1\2', text)
   ```
3. **OCR Typo Normalization**: Corrects frequent character misrecognitions common in Indian Supreme Court scans:
   * `C0urt` / `C0URT` $\rightarrow$ `Court` / `COURT`
   * `Judgm3nt` / `JUDGM3NT` $\rightarrow$ `Judgment` / `JUDGMENT`
   * `Appe3llant` / `App3llant` $\rightarrow$ `Appellant`
   * `Resp0ndent` $\rightarrow$ `Respondent`
   * `Jncome-tax` $\rightarrow$ `Income-tax`
   * `Govl!rnment` $\rightarrow$ `Government`
   * `0entral` $\rightarrow$ `Central`
   * `Exciieli` $\rightarrow$ `Excise`
4. **Whitespace Normalization**: Converts `\r\n` to `\n`, consolidates 3+ consecutive newlines to 2, and strips trailing intra-line spaces while preserving blank-line paragraph breaks.

## 5. Metadata Extraction Process

Implemented in `LegalMetadataExtractor` ([`cleaner_chunker.py`](file:///E:/Dummy/cleaner_chunker.py#L85-L215)):

### 5.1 Dual-Format Support (Modern & 1950+ S.C.R.)
Supreme Court judgments span from modern digital judgments (2020+) to the very first reported decisions of 1950. The extractor handles both:

| Metadata Field | Modern Judgment Format | Historical 1950+ S.C.R. Format | Extraction Strategy |
| :--- | :--- | :--- | :--- |
| **Case Number** | `CIVIL APPEAL NO. 1042 OF 2023`, `SLP (C) NO. ...`, `WRIT PETITION ...` | `[1950] S.C.R. 15`, `S.C.R. 563` | Multi-pattern regex scanning for appeal types, SLP, petitions, and SCR citations. |
| **Parties (Appellant / Respondent)** | `State of Maharashtra ... Appellant(s) VERSUS ABC Infrastructure ... Respondent(s)` | `RAM KRISHNA RAMNATH AGARWAL ... OF KAMPTEE v. SECRETARY, MUNICIPAL COMMITTEE ...` | Multi-line uppercase party block scanning before and after `VERSUS`, `VS`, or `v.`. |
| **Bench / Judges** | `Hon'ble Mr. Justice D.Y. Chandrachud, CJI`, `Hon'ble Mr. Justice P.S. Narasimha` | `[SHRI HARILAL KANIA C.J., SAIYID FAZL ALI, PATANJALI SASTRI, ... JJ.]` | Bracketed Coram parsing (`[... JJ.]`) combined with `Justice`, `CJI`, `J.` regex patterns. |
| **Date of Judgment** | `DATED: 24th February, 2023`, `February 24, 2023` | `1950 March 14`, `1950 May 26` | Matches `DATED`, `Pronounced on`, standard date patterns, and historical SCR date stamps. |

## 6. The Chunking Process in Detail

Implemented in `PageChunker` ([`cleaner_chunker.py`](file:///E:/Dummy/cleaner_chunker.py#L218-L325)):

### 6.1 Strategy: Page-Aware, Heading-Preserving Logical Chunking
Unlike generic fixed-character splitters (which naively slice text every 500 characters, splitting sentences and crossing page boundaries), our chunker uses a **4-stage structural pipeline**:

```
[ Cleaned Page Text ]
         │
         ▼
[ Stage 1: Block Splitting & Heading Isolation ]
Detect lines matching HEADING_PATTERNS (JUDGMENT, FACTS, SUBMISSIONS, ANALYSIS, Judge Opinions)
         │
         ▼
[ Stage 2: Section Heading State Inheritance ]
Current heading state stored and passed to subsequent paragraphs
         │
         ▼
[ Stage 3: Numbered-Point & Paragraph Splitting ]
Split on \n\n and regex lookahead for: 1., 2., (a), [1], etc.
         │
         ▼
[ Stage 4: Deterministic Chunk ID Generation ]
Assign: {document_id}_p{page_number}_c{chunk_index}
```

### 6.2 Key Algorithmic Steps

1. **Strict Page Boundary Isolation**:
   Chunking operates strictly inside page $N$. No chunk can ever contain text from page $N-1$ or page $N+1$.
2. **Heading Detection Regex**:
   Recognizes both standard legal sections and 1950s judge opinion delimiters:
   ```python
   HEADING_PATTERNS = [
       r'^(?:J\s*U\s*D\s*G\s*M\s*E\s*N\s*T|JUDGMENT)$',
       r'^(?:O\s*R\s*D\s*E\s*R|ORDER)$',
       r'^(?:BACKGROUND|FACTS\s+AND\s+BACKGROUND|FACTS|ISSUES|SUBMISSIONS(?:\s+OF\s+COUNSEL)?|ANALYSIS(?:\s+AND\s+CONCLUSION)?|DISCUSSION|CONCLUSION|VERDICT|OPERATIVE ORDER)$',
       r'^(?:PART\s+[A-Z0-9]+|SECTION\s+[A-Z0-9]+|POINT\s+[A-Z0-9]+)$',
       r'^[A-Z\s.]+(?:C\.J\.|JJ\.|J\.)(?:\s*[-—:].*)?$', # e.g. "FAZL ALI J. -"
   ]
   ```
3. **Heading Inheritance**:
   When a heading line (e.g. `FACTS AND BACKGROUND` or `## **JUDGMENT**`) is detected, it updates `current_heading`. Rather than emitting an empty chunk for the title, all subsequent paragraphs under that section inherit `section_heading: "FACTS AND BACKGROUND"`.
4. **Numbered Paragraph Sub-splitting**:
   Judgments organize their reasoning by numbered paragraphs. The chunker sub-splits blocks using lookahead regex:
   ```python
   sub_points = re.split(r'\n(?=\d+\.\s+|\[\d+\]\s+|\([a-z0-9]+\)\s+)', block)
   ```
   This ensures each distinct point (`1. Leave granted...`, `2. The primary question...`) forms an independent, coherent chunk.
5. **Deterministic Chunk ID Convention**:
   Format:
   $$\text{chunk\_id} = \text{document\_id} + \text{"\_p"} + \text{page} + \text{"\_c"} + \text{index}$$
   Example: `1950_1_15_25_EN_p2_c1`

## 8. Operational Resilience & Production Controls

Implemented in `IngestionPipeline` ([`pipeline.py`](file:///E:/Dummy/pipeline.py)):

1. **SHA-256 Duplicate Detection**:
   Computes the cryptographic SHA-256 hash of each PDF before processing. If identical file content has already been processed, it is instantly skipped (`SKIPPED_DUPLICATE`) without re-running OCR or parsing.
2. **Resumable State Management**:
   Maintains `ingestion_state.json`. If a batch run of 43,000 files is interrupted, restarting it will resume exactly where it stopped, saving cloud credits and compute time.
3. **Exponential Backoff Retries**:
   Page extraction is wrapped with `@retry` from the `tenacity` library (3 attempts with exponential delay from 2s to 10s) to handle transient network hiccups.
4. **Defect Tracking & Error Isolation**:
   If any file fails to process, the failure is isolated. It does not crash the batch job. A complete traceback is appended to `reports/status_error_report.json` with document ID, file path, and error timestamp.
